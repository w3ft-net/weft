# Shard claim flow — my current understanding, the bug as I see it, and where I'm uncertain

I want to write this down explicitly because in my last message I jumped to a
diagnosis ("reconciler doesn't pre-mint LAUNCHING rows ahead of an instance
refresh") that you pushed back on, and I should slow down and re-derive from the
code rather than guess.

## How a shard is *supposed* to be claimed (my reading of the code)

Steady state — async-launcher path (the one prod uses for every shard tier):

1. **Reconciler tick** (every `PollInterval`, default `5 * time.Minute` in
   prod, `5 * time.Second` in dev). For each bucket:
   - Read `Entries` from the registry (now populated from the DB at boot via
     `LoadFromStore` since `929c959`).
   - Count `IngestingCount` from those entries.
   - Count `LaunchingCount` from `shard_records` (the DB).
   - Compute `effective = LaunchingCount + IngestingCount`. For each
     `i := effective; i < bucket.Target; i++`, emit one `LaunchShardOp`.
   - `LaunchShardOp.Apply` → `provisionForBucket` → `mintLaunchingRow` →
     `INSERT INTO shard_records (... state='LAUNCHING' ...)`.
   - Then `syncASGDesiredCapacity` sets the ASG's `desired_capacity` to
     `target + future_launching + read_only`. ASG launches an instance to
     match.

2. **Lifecycle hook** fires when an ASG-launched instance enters
   `Pending:Wait` (transition `autoscaling:EC2_INSTANCE_LAUNCHING`,
   `DefaultResult: ABANDON`, `HeartbeatTimeout: 600s`):
   - The hook calls `ClaimLaunchingForTier(tier, instanceID)`. This is a
     `SELECT ... FOR UPDATE SKIP LOCKED` on the **oldest LAUNCHING row whose
     instance_id is empty**, then an UPDATE that stamps the row's
     `instance_id`.
   - On claim: tag the EBS volume with the row's shard_id, `CompleteLifecycleAction(CONTINUE)`.
   - On no claim: `CompleteLifecycleAction(ABANDON)` → ASG terminates.

3. **First heartbeat from the new shard process** lands at the coordinator.
   `provisioner.christen` looks up `FindLaunchingByInstance(instanceID)`,
   reads the row's window/apps/heartbeat-token, dials the shard's
   Configure RPC, and on success transitions registry+DB to `INGESTING`.

So the order is: **reconciler MINTS the row → ASG launches instance → hook
CLAIMS the row → instance heartbeats → christen promotes to INGESTING.**
Without a row to claim, the hook ABANDONs.

## What I think the bug is (re-derived, slowly)

The activities log shows two distinct refresh attempts in the last few minutes,
each with the same shape:

```
T+0    Refresh terminates an InService instance ("instance refresh").
T+1ish Refresh launches a replacement.
T+5–7s Replacement instance hits hook.
       Hook calls ClaimLaunchingForTier — returns (zero, false).
       Hook ABANDONs. Cancelled.
T+~30s ASG sees desired > actual → launches another (Cause: "difference
       between desired and actual capacity"). This one succeeds.
```

So the failing claim happens specifically on instances launched via
**`Cause: "an instance was launched in response to an instance refresh"`**
(StartTime = the moment AWS picked one to roll). The instances that
ASG launches a few seconds later via **`Cause: "difference between desired
and actual capacity"`** do succeed.

What I'm now uncertain about, and where my last message was probably
overconfident:

- **Do refresh-launched instances bypass `desired_capacity`?** I don't actually
  know this. If the refresh uses a different code path that doesn't bump
  `desired`, then `syncASGDesiredCapacity` couldn't have noticed in time
  to mint anything for them. This is probably what's happening, but I haven't
  verified.

- **What's the bucket target right now?** Earlier today (pre-deploy) it was 2.
  After the zombie was archived, target should still be 2. Looking at the DB
  snapshot you pulled earlier: `target_ingesting_count=2`, `IngestingCount=2`
  (the new christened shard + the original healthy one). So under normal
  conditions, when both INGESTING shards are healthy, **the reconciler should
  emit zero LaunchShardOps and there should be zero LAUNCHING rows in the
  DB.** That's the expected steady state.

- **The hook expects to claim a LAUNCHING row.** But if no LAUNCHING row exists
  (because the fleet is already at target), what *should* the hook do? Looking
  at `lifecycle.go:215` — it's hardcoded to `DecisionAbandon`. There is **no
  branch** for "the fleet is at target and you're a surprise instance." The
  only way the hook ever succeeds is if something else minted a LAUNCHING row
  before the hook ran.

So my current best guess is something like: **the hook's `claim or abandon`
posture assumes the reconciler is the only thing that ever asks for new
instances. An instance refresh is initiated outside the reconciler's view —
AWS terminates one of mine, replaces it, but the reconciler hasn't had a
tick to notice the loss yet, so no LAUNCHING row is in flight, so the
hook ABANDONs.** Then the *next* reconciler tick (or the ASG's
`desired > actual` reaction) catches up, mints a row, and the second
launch succeeds.

I think this is plausible but I have not yet:

1. Confirmed by reading code that an `instance refresh` increments
   `desired_capacity`. (If it doesn't, then `syncASGDesiredCapacity` couldn't
   help even if it ran instantly.)
2. Confirmed how AWS's "in response to an instance refresh" launches reach
   the coordinator's awareness. The reaper notices a registry entry whose
   heartbeat went stale — but the refresh terminates the instance abruptly,
   so there's a race window of `staleAfter ~ 60s` where the registry still
   thinks the instance is alive while the hook is already firing on the
   replacement.
3. Looked at what `MinHealthyPercentage` actually does (I gestured at it in
   the previous message but didn't verify the semantics for this lifecycle
   shape). I asserted it would force terminate-after-replace. Need to
   confirm.

## What I'd want to do

In rough order:

1. **Stop guessing — let the current refresh finish or cancel it cleanly.**
   The current activities show the loop is converging in a clumsy way (each
   ABANDON is followed by a successful launch the reconciler caught up with),
   not stuck. So nothing's on fire; the question is "how do we make refreshes
   not produce these failed-claim transients."

2. **Read what an `instance refresh` actually does to ASG `desired_capacity`
   and to the lifecycle hook timing.** If refresh maintains desired and the
   reconciler+`syncASGDesiredCapacity` path can't notice the imminent loss
   in time, then the right fix is on the coordinator side: either pre-mint
   LAUNCHING rows opportunistically, or have the hook tolerate "no row
   waiting for me" by minting one inline before claiming.

3. **Decide the policy question**: should the hook ever `CONTINUE` an
   instance that has no LAUNCHING row waiting for it? Today it cannot —
   the row carries the shard_id, window, apps, and heartbeat-token, all of
   which the hook needs to complete. So a "tolerate surprise instance"
   branch would have to mint the row inline (claim-or-mint-then-claim).
   That's a real semantic change, not just a timing fix; worth thinking
   through.

4. **Once the cause is confirmed**, write the test that pins it (a
   harness that simulates a refresh-style termination + immediate hook
   call), then fix.
