## Style observations
- No explanation of revoking/listing/rotating tokens or token lifetime/expiry; "it's only shown once" has no recovery path stated.
- Line 31 "from the CLI:" does not say whether the user must be logged in/permissions (group) needed.
- Line 38-39 "no path contortions required" is informal.
- Paragraph at 37-46 mixes ingest (env stamping) with path layout; "the three-segment layout" referenced before defined as vs 4-segment.
- No warp, Windows, coming soon; "watch" absent. Env spelled "env" and "deployment environment" inconsistently with the `DEPLOYMENT` meta-var (schema-setup doc lists DEPLOYMENT and ENV separately) - possible terminology confusion.

## Findings
- tok-02 (line 12): doc says each token is scoped to a single namespace; `--namespace acme,globex` created a 2-namespace token (listed as `acme,globex`). Product bug or doc stale; ambiguous. Decide: validate a single ns, or say "one or more namespaces (comma-separated)".
- tok-18/19 (lines 39-42): doc presents 3-segment `/log/myco/api/main.log` as the plain-app layout; with env-bound tokens real paths are `/log/acme/prod/api/main.log`; `/log/acme/api` => `file does not exist`. Doc probably stale/ambiguous. Proposed: "Rows from an env-bound token land at `/log/myco/<env>/<service>/<kind>.log`; a token with no env lands at `/log/myco/<service>/<kind>.log`." (no-env case not verified).
- tok-20/21 (line 42): heartbeats.log and runtime.log not present in any listing; likely data-dependent, wording could say "when the agent emits them".
- tok-23 (lines 43-44): "a token spanning multiple envs" is misleading; any env-bound token yields the 4-segment form. Doc ambiguous.
- tok-05/27 (style): no mention of `weft token list` / `weft token revoke --id`; token-only-shown-once has no recovery path. `weft token --help` is unsupported (`unknown token command`).
- tok-12: CLI prints `Token created: wft_...`, whereas connect-heroku manual shows `issued: wft_...` (other doc stale, not this one).
- Cleanup: created 2 tokens, ids 19 and 20 (audit-tokens-x, audit-tokens-1), both revoked; they stay listed as revoked. The second was an exploratory multi-namespace attempt that succeeded unexpectedly.
