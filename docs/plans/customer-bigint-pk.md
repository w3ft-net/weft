# Customer (organization) primary key: uuid → bigint

**Status:** done. Written 2026-10-01; cut over to production 2026-10-03
(see Phase 5 for what actually happened and what the plan missed).

## Why

The tenant boundary is keyed by a user-chosen string, the org `name`
(`organizations.name`, unique index `idx_customers_name`). That string is
the `customer` on every `LogRow`, the `customer` column in every shard
and parquet file, the `customer_name` in the usage/Stripe tables, and a
segment of the Redis tail channel. Consequences found during C1
(`docs/audit_0926.md`):

- A name containing `:`, `*`, `?`, `[` can make its Redis channel/pattern
  collide with or cover another tenant's. No validation exists beyond
  lowercase+trim at signup (`api/handlers.go:486`).
- The name is denormalized into every row of shard data, so an org rename
  would mean rewriting parquet.
- It is the widest possible RLS key: a string compare on every shard scan.

`organizations.id` is a `uuid` today, so the "natural" int64 does not
exist yet; this plan creates it.

## Target

- `organizations.id` becomes `bigint GENERATED ALWAYS AS IDENTITY`
  (what `bigserial` expands to on modern Postgres; use identity unless you
  specifically want the legacy sequence ownership semantics).
- Every `org_id uuid` FK becomes `bigint`.
- Shard rows carry `customer_id BIGINT`; the proto carries `int64
  customer_id`; the Redis channel is `tail:<id>:<ns>:<svc>:<kind>`
  (no user-controlled text in the customer segment, so the collision
  class disappears structurally).
- **Names stay at the edge.** `X-Active-Org`, JWT display claims, CLI
  flags, the web UI and `weft-go` keep speaking names. The session builder
  (`auth/session.go`) resolves name → id once; everything behind it uses
  the id. The frontend has zero `org_id` references, so the user-facing
  surface does not change.

## Blast radius (measured 2026-10-01)

| Area | Size |
|---|---|
| Postgres tables with `org_id uuid` | 15 (+ `users.last_active_org_id`) |
| Postgres tables with `customer_name text` | 5 (`usage_hourly`, `usage_daily`, `stripe_usage_reports`, + defaults) |
| `shard_archive_stats.customer` | 1 (keyed by name; janitor retention depends on it) |
| FKs to `organizations(id)` | 7 explicit |
| Go files referencing `OrgID` / `CustomerName` / `.Customer` | ~66 / ~27 / ~32 |
| Proto messages with `string customer` | ~25 |
| Shard DuckDB schema | `shard/shard.go:193` `customer TEXT`; `shard/compact.go` cutoffs |
| Archived parquet in S3 | every archived shard (immutable) |

## Decisions (settled 2026-10-01)

- **Only two tenants matter: graybeard and loom.** They get ids `1` and
  `2`, set by hand; the sequence is then advanced past them
  (`setval(..., 2)` so the next org is `3`). Any other org row, and its
  data, is deleted before the migration runs. Confirm the exact org
  `name` values and what else is in prod at execution time.
- **No dual write, no compatibility predicate, no parquet rewrite.**
  Archived log data is nuked: every archived shard's parquet and its
  `shard_archive_stats` rows are deleted, and new shards start with
  `customer_id BIGINT`. After the cutover there is exactly one code path
  and no `customer TEXT` data anywhere. (A row-level rewrite via the
  retention janitor remains possible if the history ever turns out to
  matter; it is not planned.)
- **Maintenance window**, not online migration.
- **`type OrgID int64`** in `store`, so a stray string or wrong integer is
  a compile error at each of the ~66 sites. A type, not a wrapper helper.
- **The uuid is dropped**, not kept as a public id. Nothing external is
  being checked first.
- Identity column is `GENERATED BY DEFAULT` (not `ALWAYS`), which is what
  permits the hand-set `1`/`2`. Equivalent to `bigserial` for this
  purpose.

## Phases

### Phase 1: Postgres (M) — DONE: `store/migrations/078_org_id_bigint.sql`
Written and run against a copy of prod (`prod.sql`, goose 77) on
2026-10-02 in one transaction, ~1 s. Verified: orgs are exactly
graybeard = 1 / loom = 2, next org gets 3, per-org row counts identical
before/after (`usage_hourly` 67,997/51,945; `usage_daily` 169/57;
`shard_archive_stats` 27/19), all 7 FKs valid, all 18 partitions
converted, `rollup_usage_daily()` still runs.

What it does, in one transaction:
- Maps graybeard -> 1, loom -> 2 (by `organizations.name`); deletes every
  other org (prod had 3 more: `gbc`, `gbc2`, one with an empty name, none
  with data) and its rows in tables without a cascading FK.
- Drops the 7 FKs into `organizations`, converts every `org_id uuid` in
  `public` (partitioned parents carry their partitions: `tmp_files` 2,
  `usage_daily` 8, `usage_hourly` 8 in prod) plus
  `users.last_active_org_id`, turns `organizations.id` into
  `GENERATED BY DEFAULT AS IDENTITY`, re-adds the FKs.
- Re-keys the name-keyed tables to `org_id bigint` (named `org_id` in
  Postgres, not `customer_id`, to match the other 15 tables):
  `usage_hourly`, `usage_daily`, `stripe_usage_reports`,
  `shard_archive_stats`; recreates their PK/unique/index and
  `rollup_usage_daily()`.
- Prod-only objects `schema.sql` does not show: converts
  `partman.template_public_tmp_files.org_id` (guarded; the template tables
  are owned by the app role `weft` in prod, like every other table, so no
  special privileges are needed), and drops the unused
  `public.template_public_usage_{daily,hourly}`.

### Phase 2: code to ids — DONE (`49e94c3`)
- `store.OrgID` (int64) with `String`/`ParseOrgID`; every model field and ~28
  store signatures take it. saaskit's `orgs.Store` is used unchanged (org ids
  are opaque strings there): ids cross at `store/user.go` and
  `auth/session.go` only. `Session.ActiveOrgID` is an `OrgID`; org names stay
  the user-facing key.
- `tenant.go`'s row-level-security context carries an `OrgID`; zero is
  "absent" and fails closed. (This is the one empty-check that stays: it is
  the RLS layer itself. The matcher and planner have none.)
- saaskit: `orgs.SchemaSQLBigintOrgID` added (commit `19fa77a` in
  `~/dev/lib/saaskit`, not yet tagged/pushed); `Migrate` applies it.

### Phase 3: wire + shard data — DONE
- Proto: `LogRow.customer` → reserved, `int64 customer_id = 26`;
  `CustomerArchiveStat.customer` → `int64 customer_id = 5`. The ~16 request
  messages with `string customer` are **removed (reserved), not converted**:
  the server never read them (identity comes from the verified JWT; see the
  comment in `integration/docker_test.go`), so converting would have added
  dead fields. `AuthenticateResponse.customer` and `SourceInfo.customer` stay:
  they are display names, not keys.
- The coordinator stamps `customer_id` on every row from the authenticated
  token (`IngestStream`) or the resolved parser (`ingest.Schema.CustomerID`,
  API ingest paths). Senders never set it. **weftd 0.26.0** no longer stamps
  or threads the customer; old agents keep working (their extra field is
  ignored), so there is no forced upgrade.
- Shard: `customer TEXT` → `customer_id BIGINT`; stats/cutoff queries and the
  Lambda compactor's JSON use `customer_id`. The planner emits
  `customer_id = CAST(? AS BIGINT)` (args travel as strings, like the
  timestamp bounds); `PlannerVersion` is 3, so stored lowered plans
  re-lower lazily. `RowMatcher`, the tail topic and the Redis channel
  (`tail:<id>:<ns>:<svc>:<kind>`) are keyed by the integer id, which also
  removes the glob-collision class C1 had on names.
- Usage stats, `SeenServices`, the namespace cache and the DLQ are keyed by id;
  `logdb`'s `ShardArchiveStat`/janitor use `OrgID`.
- Kept as-is on purpose: the Stripe meter-event `identifier` is still
  name-based (it is Stripe's idempotency key, so a day already posted must
  still dedupe on retry).
- Archived data: delete all archived parquet in S3 and truncate
  `shard_archive_stats` in the cutover window. Irreversible; confirm at
  execution time that nothing in the archive is wanted.
- Cold-shard Lambda and the Lambda compactor: redeploy after any Terraform
  apply (it reverts to a placeholder); AL2023/glibc build reqs apply. Their
  wire changed (`customer_id`), so deploy them with the coordinator and roll
  shards (`weft-admin roll-all`) before resuming ingest: there is no wire
  version gate between coordinator and shard.

### Phase 4: Redis — DONE (part of Phase 3)
- A rolling deploy briefly splits fan-out between old and new coordinators;
  tail is best-effort, accepted. `coordinator_desired=2` in prod, so schedule
  it with the deploy.

### Phase 5: cutover (M) — DONE 2026-10-03

Rehearsed on 2026-10-02 against a fresh copy of prod (`prod.sql`, goose 77)
through the real entry point, `go run ./cmd/weft-migrate`: 078 applied in
~1 s, goose reports 78, the saaskit schema step ran clean, a second run is a
no-op. Result: orgs are exactly graybeard = 1 / loom = 2, every per-org row
count identical, all 5 users keep an active membership, no dangling
`last_active_org_id`. (The 3 orgs it deletes: `gbc`, `gbc2`, and one with an
empty name and no data. The empty one is most likely what the old
`resolveOrgID("")` created for an org-less session; that call is gone.)

**How the migration is triggered matters.** `weft-migrate` runs from the
coordinator ASG launch lifecycle hook, so the *first new coordinator to boot*
applies 078, and from that instant every old coordinator is running against a
schema it does not understand. Do not roll coordinators one at a time. Order:

1. Stop ingest (agents buffer/retry; weftd spools).
2. Scale the old coordinators to 0 (`coordinator_desired` is 2 in prod).
3. Merge; CI builds and rolls the new coordinator AMI. The launch hook runs
   `weft-migrate`; the advisory lock serializes concurrent new instances.
4. Roll shards (`weft-admin roll-all`), then redeploy the cold-shard Lambda and
   the Lambda compactor (Terraform apply reverts the Lambda to a placeholder).
   Their wire changed and there is no coordinator<->shard version gate, so do
   this before resuming ingest.
5. Smoke-test with a minted JWT: `weft` login, a tail, a cron, a dashboard,
   a usage query.
6. Delete the archive last (all archived parquet in S3, truncate
   `shard_archive_stats`), after 3-5 are verified. Irreversible.
7. Resume ingest. Then `make collapse`; drop stale `weft_test_<slot>` pool DBs
   first so the new migration applies in tests.

Before step 1:
- saaskit `v0.3.3` is published and weft pins it (done).
- Privileges are not a concern: in the prod dump the app role `weft` owns
  every object 078 alters (698 objects, including the partman template
  tables). `rdsadmin` owns only `partman.part_config*` and `rds_superuser`
  owns the `cron` tables; the migration touches neither. The rehearsal ran as
  a local `weft` role, matching prod's ownership.
- Release weftd 0.26.0 whenever convenient. It is not required for cutover (old
  agents keep working), and kevcons apps run the pinned `.deb`, so a release
  plus repin is needed for the dead plumbing to leave the fleet.

#### What happened (2026-10-03) and what the plan missed

Prod was down 2026-10-02 11:28 EDT to 2026-10-03 09:14 EDT, far longer than the
plan assumed, mostly because the status-server deploy failed once and the
window sat open overnight. Order actually run: coordinator ASG to min 0 /
desired 0, merge #14, status deploy (AMI + launch-template bump), scale up to
min 1 / desired 2 (the first new coordinators ran `weft-migrate`; goose
reported version 78), `bump-shard-templates` + `roll-all`, then the archive
delete and `shard_archive_stats` truncate. Phase 5's unplanned work:

- **Shard volumes carried the old schema.** The plan covered archived
  parquet only. Rolled shards reattach their EBS volume, whose `logs` table
  had `customer TEXT`; `CREATE TABLE IF NOT EXISTS` left it alone, so ingest
  failed with "the column must exist in the table". Fixed in #15
  (`convertLegacyCustomerColumn`: add `customer_id`, backfill graybeard=1 /
  loom=2, any other name NULL, drop `customer`; on a 3 GB volume it took
  about 25 s on open). Cutover-only, and since removed: once the four live
  volumes were converted (the only shard-data volumes in the account; no
  orphans, and every snapshot is an 8 GB AMI root), nothing could reattach an
  old-schema volume. A shard that opens one now fails at ingest; clear a stale
  `dev/shard-data` with `make integration-clean`. A rehearsal that opens a copy
  of a real shard volume would have caught this: the Postgres rehearsal could
  not.
- **An unrelated commit rode in on the branch.** `987d60d` ("fix tenant leak
  in tail -f") had swept in the in-progress democast extraction (`replace
  ../democast`), which broke CI and the AMI build. Removed from the branch
  before merge; the work is on local branch `democast-wip`.
- **The status deploy failed once, then passed.** `build: repository has
  uncommitted changes` three seconds in; the cause was never found (the
  workdir was clean as `status-build` under every `HOME` we tried) and a
  retry passed. kevcons's `hasUncommittedChanges` discards git's stderr and
  reports "dirty" on any git failure, so a real cause would be invisible.
- **Scaling the coordinator ASG to 0 does not stop the deploy.** The status
  server built the AMI, bumped the launch template and "rolled" the empty
  group successfully, but its post-deploy steps (`bump-shard-templates`,
  `roll-all`) need a running coordinator, so they did not run until the
  second deploy. Scale up before expecting the shard roll.
- **The Lambdas need no manual step.** `release.yml`, triggered by the status
  server after a healthy deploy, rebuilds and redeploys both on every release.
- **`make collapse` ran by itself** (bot commit after the healthy deploy).
- **Tooling gaps found:** `kevcons ssh --role X --instance-id I --command C`
  ignores `--command` (opens an interactive session); `kevcons ssh --name
  <tag>` was added for the status server (management account, no ASG); the
  shard systemd unit logs to `/opt/app/logs/shard.log`, not the journal.

## Risks

- **Test pool DBs skip new migrations** (version recorded by number):
  expect mysterious "table missing" until dropped.
- **The archive delete is irreversible.** Run it last in the window,
  after the Postgres migration and the new build are verified. Also add a
  two-tenant regression test in the shape of C1's for the `customer_id`
  predicate.
- **Sequential ids are enumerable.** Safe only because RLS is the
  predicate, not secrecy. Do not expose the integer in URLs or API
  responses; the edge stays names.
- **Wire skew:** old coordinator + new shard (or reverse) during the
  deploy. The wire-version bump is what makes this fail loudly instead of
  silently dropping `customer_id`.

## Out of scope

Renaming orgs (becomes cheap afterwards, but not built here), per-org
sharding/placement changes, and callbox (separate service, keyed on its
own tenant ids).
